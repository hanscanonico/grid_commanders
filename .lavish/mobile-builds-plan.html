Mobile Builds — the whole command table in two hands

The engine profile was already right and still is: Godot 4.7.1, a 640×360 landscape canvas under canvas_items stretch, gl_compatibility on desktop and mobile (project.godot:190–194), ordinary Button chrome, a complete joypad map, and every persisted byte already under user://. What is missing is not simulation and not rendering. It is the last metre of interaction and a package. A tap already selects a unit, walks it, confirms an attack, buys a tank and ends a turn — because Godot emulates a mouse from touch and every one of those routes is a click or a real Button. But eight interactions in this game exist only on a key, and the worst of them is destructive: on a bare touchscreen a player who opens Hammerfall's aiming state has no way out except to fire it.

This plan ships Android first, keeps every rule where it is, and treats mobile as what it is — presentation and packaging. Nine milestones, three of them small. The merge bar throughout is the one the art programme already uses: make smoke byte-stable across all 85 scenarios, because mobile chrome does not exist on a desktop build.

Where this stands — a touch-complete game, minus eight routes

Every claim below is a read of main @ 2ab1adbe. The baseline that makes most of the game work already is a default nobody wrote down: project.godot declares no [input_devices] section, so Godot's emulate_mouse_from_touch stays on and emulate_touch_from_mouse stays off. A tap therefore arrives as an InputEventMouseMotion followed by a left InputEventMouseButton — which is exactly what scenes/battle/battle.gd:576–587 is written against. There is no touch code anywhere in the repository: no InputEventScreenTouch, no InputEventScreenDrag, no gesture class, no get_display_safe_area, and not one OS.has_feature outside addons/.

What already works on a bare touchscreen

  • The whole command loop — cursor placement, unit select, path preview, move, attack confirm, transport drop, build and preview all land in confirm_at through the mouse-button arm at battle.gd:581–587.
  • Every menu — the action menu's rows are real Buttons (scenes/ui/action_menu.gd:62–74), a Cancel row is appended to every one of them (scenes/battle/battle_menus.gd:25,217), and value rows cycle forward on a tap (action_menu.gd:140–142).
  • End Turn and FIRE — both are ordinary buttons on the bottom bar (scenes/ui/hud_bottom_bar.gd:166,178), so the two match-shaping commands were never keyboard-only.
  • Threat, Range and Objectives — the top bar's chips are _chip_buttons that dispatch the action they name (scenes/ui/hud_top_bar.gd:87,93,98). The dock this plan adds owes nothing for these three.
  • The handoff blackout — dismissed by TransitionInput.is_confirm, which accepts a left click (scenes/common/transition_input.gd:11–16), and there is a real button under it too (scenes/battle/battle.tscn:238, wired at battle.gd:77).
  • Banners, cut-in skips and the victory lockup — all accept a mouse press today, so they accept an emulated tap.
  • Persistence — user://settings.cfg (autoload/settings.gd:23), user://save.json (core/save_game.gd:31), user://replays/ (core/replay_file.gd:34) and user://campaigns/ (core/campaign/campaign_profile.gd:21). No FileDialog anywhere. Nothing to port.

What a touchscreen simply cannot reach

  • Back / Cancel in the four states that have somewhere to go back to — UNIT_SELECTED, TARGETING, DROP_TARGETING, POWER_TARGETING. _cancel() (battle.gd:690–709) is reachable only through the cancel action (battle.gd:591).
  • Pause a computer turn — battle.gd:543–546, cancel only. Resume one — battle.gd:552–559, confirm only, and the comment there says a click is deliberately not a resume.
  • Zoom — battle.gd:574 hands the event to BattleZoom.handle_input (scenes/battle/battle_zoom.gd:67–75), which listens for zoom_in/zoom_out: wheel, =/-, keypad, or a pad shoulder. A phone has none of them.
  • Next ready unit — the chip exists but is a UiTheme.hud_label, not a button (hud_top_bar.gd:104).
  • Replay step — replay_step is bound to S and nothing else (project.godot:172), consumed at battle.gd:565–567.
  • Fast forward — polled with Input.is_action_pressed (scenes/common/fast_forward.gd:29–30), so it needs a held control, not a tap. Deliberately out of the first release — D2 says why, §7 lists it.
  • Tooltips — unverified on device, and one of them provably unreachable by focus. Tooltip.attach opens on mouse_entered or focus_entered (scenes/ui/tooltip.gd:118,120), and follow_focus's door — the one the segmented controls and the illustrated rows use (tooltip.gd:148–150) — is shut to anything but the keyboard by FocusSource.by_keyboard (tooltip.gd:255–256, scenes/ui/focus_source.gd:36–42). The hover door may or may not open on a phone: under emulate_mouse_from_touch a press-and-hold synthesises motion, so mouse_entered can fire on a real device. Nobody has measured it, so this is a device check (MB4) and not a finding. What is not in doubt is the one trigger no focus source can ever reach: the disabled Continue button (scenes/menu/main_menu.gd:652) — a disabled control takes no focus, and its own comment banks on the pointer instead (main_menu.gd:649–651, "a disabled control still answers the pointer"). That one needs an answer that is not a tooltip.
  • A package — no export_presets.cfg, no make export target among the Makefile's three dozen, and only 4.1.2.stable templates installed against a 4.7.1.stable engine.

The dead ends, ranked

A missing route is an annoyance. A missing route out of a state is a bug, and this is the ranked list the milestone order is built on. The first is the only destructive one.

1 · POWER_TARGETING — destructive, no abort

Radek Morn's Hammerfall is aimed, and in the aiming state any tap on the board calls _fire_aimed_power(cell) (battle.gd:669–670); PowerCommand.validate refuses an off-board target and nothing else, which is the more-commanders plan's D2. The only abort is the cancel action (battle.gd:704–709), and it is the one branch that deliberately spends nothing. A touch player who opens the aiming state must fire the most expensive power in the game, at a cell they did not choose. This is why MB3's headline is not "a Back button" but "the abort".

2 · PAUSED — no exit

Resume is the confirm key alone, and Esc reopens the map menu whose Cancel row returns to rest_state() (battle.gd:444–445) — which, mid-computer-turn, is PAUSED again. A touch player who somehow reached the pause cannot leave it.

3 · AI_TURN — no route to any menu, and in a watched match no route out at all

A tap during a computer turn earns _reject("CPU turn.") (battle.gd:671–672). In a replay playback or an AI-vs-AI watch every turn is a computer turn, so on a phone there is no touch route to pause, to the map menu, or back to the main menu. The pause seam exists and is well designed — Battle.pause_gate (battle.gd:398) — it simply has no touchable door.

4 · TARGETING / DROP_TARGETING — refusals with no way back

An off-target tap answers "No target there." or "Cannot unload there." (battle.gd:659–668) forever. The command is not lost — the unit is mid-order — but the order cannot be abandoned.

5 · UNIT_SELECTED — one escape, and it is undiscoverable

A tap out of reach answers "Out of reach." (battle.gd:658). The single way out is to tap the unit's own cell — a zero-length move into the action menu (battle.gd:643–645) — and then Cancel, which runs _undo_move_preview (battle.gd:1316). Nothing on screen says so.

6 · Replay playback is keyboard-only

Esc parks the runner, S takes one command. Neither has a control. With dead ends 2 and 3, the replay plan's whole control set is off the table on a phone.

7 · The zoom is frozen at the opening rung

On Bulwark the floor rung is 0.568, which frames the whole 49×32 board — a cell is then about 9 canvas pixels, roughly 1.5 mm on a 6.1" phone. There is no touch way to zoom in, so the largest board in the game is unplayable rather than merely awkward.

8 · The tooltips are unverified on device, and one of them cannot work at all

The focus door is shut to a finger by FocusSource.by_keyboard; the hover door might not be, because emulate_mouse_from_touch synthesises motion and a press-and-hold may already raise mouse_entered on a phone. That is a measurement MB4 takes before it writes a third focus source, and it is the gate on whether that work is scoped at all. The exception needs no measurement: the greyed-out Continue button takes no focus by definition, so its explanation cannot be recovered by any focus source, and — if the hover reading comes back negative — cannot be recovered by a tooltip at all. That copy is the one case where the words exist precisely because the control cannot speak for itself, so it gets its own answer rather than a shared one.

The design — one dock, one size profile, one package

Three pieces, and they are deliberately independent: the dock closes the interaction gaps, the size profile makes what is already there hittable, and the package makes any of it reachable on a device. Each ships without the others.

The dockMB3 · MB6

MobileDock, a third bar under the two the HUD already docks, mounted only on a mobile build. Its leading chip follows Battle.state through the setter that already prints the key legend — battle.gd:139–143, whose STATE_CONTEXT table (battle.gd:45) is the one place a state is turned into what the player is told. Menu at rest, Back in the four targeting states, Pause while the computer plays, Resume and Step while paused. Beside it, always: −, +, N. Threat, Range and Objectives stay where they already are, on the top bar.

The size profileMB4

A mobile branch inside UiTheme and UiKit — the menu plan's D1 makes those two the only files a metric may live in — that inflates hit rectangles first and drawn chrome second. The order is not taste: every drawn height in the two HUD bars feeds HUD_BARS_H (ui_theme.gd:113), which feeds _board_viewport_size (battle_view.gd:741–742), which feeds min_zoom and therefore the floor rung of every board in the game.

The packageMB1 · MB5 · MB8 · MB9

export_presets.cfg with Android and iOS presets, 4.7.1 templates, make export-android, and an exclude list that keeps the editor addons out of a player build — the _mcp_game_helper autoload (project.godot:22) is 1,105 lines with a per-frame _process and a remote command surface. Plus the payload diet: 11.6 MB of uncompressed music is the single largest thing in the repository.

What the build weighs, and what runs in it

Payload

  • Music is 11.6 MB of PCM — assets/music/advance.wav 5,131,680 bytes and assets/music/parade.wav 6,513,274 bytes, imported as AudioStreamWAV with no 8-bit, mono or rate reduction. That is both package size and resident RAM. Ogg Vorbis cuts it roughly tenfold, and the sibling audio_generator pipeline behind make audio (Makefile:332–340) is where a format change belongs.
  • Six unit atlases at 1152×480, ≈68 KB each on disk but ≈2.2 MB of VRAM each — ≈13 MB resident. Fine on any 2020-onwards phone; worth knowing before anyone adds a seventh.
  • Terrain atlas 896×320, ten autotile sheets at 116 KB, portraits 728 KB, sfx 264 KB. Nothing else is close to the music.

What is running that should not be

  • _mcp_game_helper — project.godot:22 loads addons/godot_ai/runtime/game_helper.gd in every run: 1,105 lines, _process at :132, a remote command surface and a stall detector. CLAUDE.md's project-layout note records keeping it out of export builds as an open decision. D7 closes it.
  • addons/gut/ — the test framework, in the tree, with no reason to be in a package.
  • tools/, tests/, reports/, docs/, maps/fixtures/ — offline instruments and fixtures. The fixture boards are reachable only by a CLI flag no player has.

The planner's clock, stated once so nobody optimises it here

docs/difficulty_check.md:509–510 measures desktop per-turn planning at 33.2 / 37.9 / 65.7 ms with every threat dial at zero, and 63.0 / 75.6 / 105.2 ms with withdraw at 0.1 — line 522 states the rule of thumb, that each threat-map dial roughly doubles per-turn planning time. Line 753 records the shipped tiers at 15.3 → 19.9 ms (Normal) through 51.6 → 60.4 ms (Easy). A phone is two to four times slower, so 60–400 ms per computer turn, on the main thread, per computer seat — and a four-army Bulwark match plays up to three of them back to back. The AR1 plan cache is deliberately inert with fog on, so the live game gets none of its speedup. None of that is this plan's to fix: see D9.

Decisions

D1 · Mobile is presentation and packaging — nothing under core/ or ai/ learns a phone exists

proposed · carried from rev 1

Every milestone here lives in scenes/, autoload/, project.godot, export_presets.cfg, the Makefile or the asset pipeline. No OS, no DisplayServer, no feature tag, no touch class and no safe-area read may appear under core/ or ai/, and the save, replay and campaign formats do not move a byte. This is not a promise, it is a gate that already runs: tools/check_scripts.sh:325 refuses a Node or a scene path in those two directories, :335 refuses the global RNG and :345 refuses a GameSpeed or Settings read. A touch class is a scene-layer type by the same argument pacing is: a device may not move an outcome, a save or a replay. The corollary the milestones are written against is that a mobile build and a desktop build must be able to trade save files, because they are the same simulation.

Rejected: a "mobile mode" flag read inside the sim — for instance a reduced day cap, a smaller default board, or a cheaper AI tier chosen by platform. Every one of those makes the platform a balance surface, and the difficulty plan's standing rule is that a tier is an AIProfile and a label. A phone that plays a different game is a second game to balance.

D2 · The input actions stay the vocabulary, and one facade owns mobile dispatch

proposed · sharpens rev 1 D2

A touch control never calls a Battle branch of its own. It dispatches the action the keyboard already dispatches, through the idiom the top bar already uses — HudTopBar._chip_button (hud_top_bar.gd:171) wired to _send_action (:181–186), which synthesises a pressed and then a released InputEventAction and feeds both to Input.parse_input_event. One class, scenes/ui/mobile_dock.gd (MobileDock), is the single authority for what a mobile control may say, and it never copies a transition out of Battle. The full vocabulary it owes, stated now rather than discovered later: cancel (Back / Menu), zoom_in, zoom_out, next_unit, replay_step, plus pause and resume — and those last two are the deliberate exception, because Battle already publishes request_pause() (battle.gd:386) and resume_turn() (:423) as named entry points, which is a better door than re-synthesising a key. show_range, show_threat, show_objectives, fire_power and end_turn already have visible controls and the dock adds none.

fast_forward is the one action in the map the dock deliberately does not carry, and it is out of the first release entirely (§7). Every other action is momentary: it is dispatched, it is consumed, it is over. Fast forward is held — FastForward.held() polls Input.is_action_pressed (scenes/common/fast_forward.gd:29–30) and rate() is read per frame — so a chip that synthesises a pressed-then-released InputEventAction, which is the whole idiom of D2, cannot express it. Giving it a control means either a press-and-hold chip with its own timing (a second input convention, on the platform where R1 says one tap must produce one receipt) or a latched toggle (a second piece of pacing state beside GameSpeed's tier, which is the device preference that already answers "make this faster" and answers it durably rather than for as long as a thumb stays down). The game-speed tier is the touch player's fast forward, it is reachable from the map menu's value rows today, and it costs the dock nothing. A press-and-hold chip is a considered follow-up after MB8 reports what the pacing actually feels like on a device — not a gap this release is leaving by oversight.

The leading chip's label is not a state machine of its own: it reads Battle.state through the same setter that already swaps the key legend (battle.gd:139–143, table at :45). One setter, two consumers. A dock that watched for state changes some other way would be the second answer that entry exists to prevent — "never refreshed from the dozen sites that assign the state" is its own comment.

One consequence has to be tested rather than assumed. _send_action injects an InputEventAction, and TransitionInput.is_press accepts that class (transition_input.gd:28–29) — so a dock press that lands while a banner is up can both do its job and skip the banner. One physical tap must produce one receipt, and MB3's proof is a scenario that says so, not a paragraph that hopes so.

Rejected: a touch-specific input path inside battle.gd — a _touch_input beside _unhandled_input, or dock buttons calling _cancel(), confirm_at() and the selection helpers directly. That is a second state machine beside Battle.state, and the first divergence between it and the keyboard path is a bug no desktop test can see.

D3 · Touch completeness beats gesture purity — and a pinch settles on a rung

proposed · carried and extended

Every interaction gets a visible control before any of them gets a gesture. A gesture is undiscoverable, unlabelable and unphotographable; a button is all three. So MB3 ships buttons for zoom and MB6 adds pinch on top of them, never instead. The ordering is also a risk ordering: buttons cannot fight the board's own tap handling, and a drag can.

When the pinch lands it obeys the ladder, and the rules are the ladder's rather than the gesture's. A pinch may run continuously during the drag, but on release it settles on a rung through BattleZoom.set_zoom (battle_zoom.gd:60–61), never resting between two — because a fractional rest is exactly the crawling-edge defect the whole-rung ladder exists to prevent, and tests/unit/test_texel_stability.gd is what holds it. Pinching out clamps to the board's floor rung, which is floor_for's answer and is 0.568 on Bulwark, not 1.0. The gesture never writes camera.zoom and never writes camera.offset: BattleView._apply_board_offset (battle_view.gd:701–702) stays the only writer, composing BOARD_LIFT_PX / camera.zoom.y. A one-finger pan rests on whole world pixels, which is the animation milestone's A3 — position_smoothing was switched off for exactly this reason and a gesture must not bring the fractional rest back by another door.

Rejected: a continuous free zoom on mobile, on the argument that a phone's screen is small enough to want one. It would put the board at a fractional rung for the whole match on the one platform where the picture is already being resampled by the window scale, and it would make "which rungs exist" have two answers — the ladder's on desktop and the gesture's on mobile.

D4 · The first release keeps the 640×360 landscape canvas, letterboxed; the aspect question is one decision, deferred whole

proposed · sharpens rev 1 D4

project.godot:26–31 is right as it stands: canvas_items stretch over 640×360 with aspect="keep". MB1 adds exactly one line — display/window/handheld/orientation="landscape" — which declares what the engine already defaults to, so no pixel moves and the declaration is what a portrait rotation is refused by. scale_mode stays absent, because on the Android targets the window scale is already whole (3.000 and 2.000) and integer mode buys nothing there; whether iOS wants a per-platform override is a measurement MB9 takes on a device, recorded in §2 and deliberately not decided here.

Aspect expand and safe-area handling are one decision and ship together or not at all, in MB7. They are inseparable because keep is currently what makes the notch harmless: the letterbox bars are where the cutout lands. There is zero safe-area handling in the repository, the HUD bars dock to the canvas edges (the bottom bar spans full width), and the only inset anywhere is HUD_EDGE = 2 (ui_theme.gd:115). The moment the canvas expands, the cutout eats the top bar's left end and the home indicator sits under the bottom bar — so shipping expand without a SafeArea authority ships a broken HUD, and shipping the authority without expand is dead code. keep costs about 210 device pixels a side on a 19.5:9 phone, roughly 18% of the screen. That is the price of the deferral and it is stated so nobody pays it twice by accident.

Rejected: widening the design canvas (say to 800×360) so 20:9 fills natively. It changes _viewport_size for every board, which changes floor_for, which changes the opening rung of every map and every one of the 85 smoke frames — on desktop, for a mobile benefit. If the letterbox proves intolerable on a device, MB7's variable-width expand is the answer, because there the width is a runtime fact the desktop never sees.

D5 · Desktop pixels do not move — the gate is OS.has_feature("mobile") and the bar is make smoke

proposed · carried from rev 1

The dock and the mobile size profile are built only when OS.has_feature("mobile") answers true, or when the presentation-only flag --mobile is passed — read through CmdArgs.flag() like every other switch, and presentation-only in the strict sense: it reaches no MatchRequest field, no save and no replay, and a match played with it resolves identically. It exists so a mobile frame can be photographed on a desktop machine, which is what makes MB3 and MB4 reviewable at all. On a desktop build the mobile chrome is not merely hidden, it is never constructed, so all 85 make smoke scenarios and make screenshot stay byte-identical, and that byte-diff is the merge bar for every milestone here.

The coupling that makes this more than hygiene: BattleView._apply_board_offset (battle_view.gd:701–702) is the only writer of camera.offset, and BOARD_LIFT_PX (:50) is derived from the two bar heights. A third docked bar therefore has to feed HUD_BARS_H (ui_theme.gd:113) → _board_viewport_size (battle_view.gd:741–742) → min_zoom (:709) → the ladder floor, through those authorities and not around them. A dock that overlaid the board instead would leave the camera framing a strip it no longer owns, and the board would be playable behind chrome.

Under a banner, a cut-in, the handoff blackout and the victory lockup the dock is docked and dead: every chip disabled, the bar never hidden. That is ux-recovery D3 ("no interactive menu may sit under a banner or a cut-in") read for a third bar, and it needs no new seam, because the bottom bar has answered it that way since before this plan: Battle.state's setter calls BattleView.refresh_keys(context) (battle.gd:139–143, battle_view.gd:533–535), which prints the legend and sets hud_bottom.show_end_turn(BattleLegend.commands_board(context)) — and show_end_turn is one line, _end_turn_button.disabled = not offered (scenes/ui/hud_bottom_bar.gd:327–330). The dock takes the same call: refresh_keys gains a third consumer, so the legend, End Turn and the dock cannot disagree about whose board it is, and no dock chip is ever refreshed from a call site that assigns a state. Which states close it is not a new list either — battle.gd:572 already names the ones that swallow board input (ANIMATING, covering every banner and cut-in, plus MENU, CONFIRM, VICTORY and INFO), and HANDOFF is refused a line earlier at :538. PAUSED and AI_TURN are the deliberate opposites: those are the two states the dock exists for. Disabled rather than hidden, because a bar that vanished under every banner would reflow the board — HUD_BARS_H → the ladder floor, R2's whole coupling — several times a turn.

Rejected: a floating, translucent dock over the board, which needs no ladder change. It breaks the HUD's standing rule that chrome swallows the pointer (both bars are MOUSE_FILTER_STOP precisely so events cannot fall through to cells rendered behind them), and on the smallest boards it would cover the cells a player most needs.

D6 · Android establishes the contract; iOS repeats it

proposed · carried from rev 1

The touch contract, the dock, the size profile and the payload diet are all proven on Android first, and iOS (MB9) is the same result carried through Xcode plus the two things only iOS has: a fractional device scale and a home indicator. The toolchain reality is that neither platform can be exported today — installed templates are 4.1.2.stable against a 4.7.1.stable.official.a13da4feb engine, so MB1's first act is fetching 4.7.1 templates. What Android has going for it is that everything else is present: OpenJDK 21.0.1 at /usr/bin/java (Godot targets 17; 21 is fine for a plain export), an SDK at ~/Library/Android/sdk with build-tools, platform-tools, accepted licenses and platforms android-33/34, and no NDK needed for a GDScript-only project. Xcode is present too, so MB9 is sequencing rather than a blocker.

Rejected: shipping both platforms from one milestone. Two toolchains, two signing stories and two device shapes in one review is where a mobile port stalls; and iOS's fractional scale is the one measurement that could send D4 back for revision, which is a bad thing to discover while also debugging a first APK.

D7 · A player build ships no editor addon

proposed · new · closes a recorded open decision

The export presets exclude addons/godot_ai/, addons/gut/, tools/, tests/, reports/, docs/ and maps/fixtures/, and the _mcp_game_helper autoload does not run in a packaged build. CLAUDE.md's project-layout note records this as an open decision — "keeping it out of export builds is an open decision, recorded here so the extra autoload is never a surprise" — and a mobile build is where it stops being deferrable: the helper is 1,105 lines with a _process at addons/godot_ai/runtime/game_helper.gd:132, a remote command surface (_handle_game_command, _game_get_scene_tree, _handle_take_screenshot) and a stall detector, on a device where a frame costs more and a remote command surface in a shipped app is a liability rather than a convenience.

Excluding the files is only half the mechanism, and the missing half is a boot error. project.godot:22 is an [autoload] entry pointing at res://addons/godot_ai/runtime/game_helper.gd. Strip the directory from the package and the entry still resolves at startup, against a script that is no longer there — a dangling autoload, which the engine reports as a load failure on the first frame of a shipped app. So the entry is turned off by a feature-tagged project setting override, autoload/_mcp_game_helper.mobile="", beside the plain entry the editor keeps. The reason it is that and not an export-time strip: an override lives in the same file the entry does, is resolved by the engine when settings load, and needs no build step — where a strip means the Makefile rewrites project.godot before an export and restores it after, which puts a mutable checked-in file in the build path and one interrupted export away from a dirty tree. If the override proves not to clear an autoload (MB1 measures it rather than assuming it), the recorded fallback is to move the registration where it belongs — the godot_ai editor plugin adding its own runtime singleton in _enter_tree, so [autoload] never names an excluded file at all. MB1's proof is not "the helper is absent" but "the build boots with no autoload error", which is the stronger reading and the one that catches this.

MB1 measured it, and the override is REFUTED on 4.7.1. The engine reads each autoload/* property raw, not through the override map: the base entry loads anyway (_mcp_game_helper was still in the tree), and the dotted key is picked up as an autoload of its own with an empty path — one "Failed to instantiate an autoload" per boot, on every platform including desktop, whether or not the named feature is active. Excluding the directory while a live [autoload] entry names it is the same error. So MB1 ships the preset without addons/godot_ai/ excluded (≈740 KB packed) and this decision's goal is outstanding: the fallback above — the plugin registering its own runtime singleton — is the remaining route, and it belongs to the addon rather than to a packaging slice.

Rejected: guarding the helper at runtime with OS.has_feature("editor") and shipping the file anyway. It leaves the code and its 1,105 lines in the package, leaves the addon a supported part of a player build in principle, and answers the size question with nothing. Excluding beats guarding when the thing has no business being there at all.

D8 · Touch targets are hit areas first, drawn chrome second

proposed · new

Every interactive control in the game is between 27% and 73% of 44 pt (§2's table), so something has to grow. What grows first is the rectangle a finger has to hit, not the rectangle the game draws — an inflated hit area is invisible to HUD_BARS_H, and an inflated drawn height is not: it moves _board_viewport_size, therefore min_zoom, therefore the floor rung of every board, therefore the opening frame of every match. A control may be painted at 7 px and answer a 44 px touch; the reverse costs the board its share of a screen it can least spare.

The mobile metric set lives in UiTheme and UiKit and nowhere else, which is the menu-revamp plan's D1 read on a second platform: UiTheme owns the recipe (a colour, a size, a stylebox) and UiKit owns the widget built from it, and a screen that kept its own copy of a metric is the drift that rule exists to prevent — pad had already done it in three files once. A mobile size is therefore a second value on an existing token, resolved once, never a per-screen if.

Rejected: a global UI scale factor on the whole canvas. It halves the board's share of the screen at a stroke — the thing the player is actually looking at — and it scales the parts that are already fine (the 8 px type reads at 24 device pixels) along with the parts that are not.

D9 · The planner is not a mobile task

proposed · new

A computer turn costs 15–105 ms on this desk (§2) and will cost 60–400 ms on a phone, on the main thread, once per computer seat. No milestone in this plan edits anything under ai/, and no AIProfile value is touched for a phone's sake. Two reasons and both are other plans': the difficulty lock says a tier is an AIProfile and a label, so a cheaper mobile tier is a fifth tier nobody measured; and the arena's D2 says a performance change is proven byte-identical with both balance reports, which is not a bar a mobile milestone should be trying to clear. The mitigation here is entirely presentational: keep the frame alive at the boundaries Battle.pause_gate (battle.gd:398) already provides, and give the player something that says the computer is thinking. The hitch is recorded as R5 rather than solved.

Rejected: moving planning to a thread, and lowering the shipped tier on mobile. The first buys a determinism problem — the sim threads a seeded RNG precisely so the same seed and commands give the same result — for a saving on the one platform least able to absorb a new class of bug. The second makes the platform a balance surface, which is D1's whole boundary.

Risks

R1 · One tap, two receipts

Godot can deliver a touch and an emulated mouse event for the same finger, and the dock's own dispatch adds a third class: _send_action injects an InputEventAction that TransitionInput.is_press accepts (transition_input.gd:28–29). The mitigation is structural — one facade owns dispatch (D2) — and the proof is a test that presses each chip during a banner and counts receipts (MOB-04). This is checked before MB6 adds gestures, because a drag that both zooms and issues a move is the same bug with a longer fuse.

R2 · The third bar and the zoom ladder are one system

A dock's height is not chrome: it is HUD_BARS_H → _board_viewport_size → min_zoom → floor_for → the opening rung of every board. Get this wrong on desktop and 85 smoke frames move; get it wrong on mobile and the camera frames a strip the dock is covering. Mitigation: the dock feeds the existing authorities rather than compensating for itself, _apply_board_offset stays the only writer of camera.offset, and the desktop byte bar catches any leak on the way in.

R3 · Safe area and expand cannot be split

Shipping expand alone puts the cutout through the top bar's left end and the home indicator under the bottom bar; shipping the SafeArea authority alone is dead code with no way to prove itself. The plan's answer is to make them one milestone and to gate that milestone on a decision, not on appetite. The standing cost of not deciding is ~18% of a 19.5:9 screen, which is a real cost and not a rounding error.

R4 · The ScrollContainer question is unanswerable from here

Godot's touch drag-scroll is gated on DisplayServer.is_touchscreen_available(), which is exactly the thing a desktop cannot report honestly. The map picker (main_menu.gd:436), the campaign hub, the end-turn guard's list, the replay list and the commander info sheet's per-card frames (commander_info_sheet.gd:202, the ▲▼ route) all depend on it, and their scrollbars are ~2 px wide. MB4's acceptance is a device check for this reason. The fallback is a wider bar in UiTheme — never a hand-rolled gesture, which would be a second scrolling authority.

R5 · The computer's turn will hitch, and this plan may not fix it

60–400 ms per computer turn on the main thread, up to three back to back on a four-army board, with the AR1 plan cache inert while fog is on. D9 forbids touching ai/, so the mitigations available are presentational: keep the frame alive at pause_gate boundaries and say the computer is thinking. MB8 measures the real number. If it is intolerable, the next step is a decision in the AI plans, not a patch here.

R6 · Fractional scale softens the pixel faces on iPhone

The display faces are pixel faces imported with subpixel positioning; at a whole 3× they are crisp and at 3.275 they are not. The remedy — per-platform scale_mode=integer — snaps 1179 to 1080 and adds bars, which is the trade the desktop playtest rejected in a different context. MB9 renders both and judges on a device. Nothing about the desktop decision is reopened either way.

R7 · The toolchain is one version behind on both ends

4.1.2 templates against a 4.7.1 engine, and Java 21 against a toolchain that targets 17. Neither is expected to bite for a GDScript-only project with no NDK requirement, but both are unproven here and MB1 is where they are proven. A template fetch failing is a bad first milestone but a cheap one.

R8 · Platform work leaks into the sim

Low, and machine-checked. tools/check_scripts.sh already refuses a Node, the global RNG and a pacing read under core/ and ai/ (:325,335,345); D1 adds OS, DisplayServer, feature tags and the touch classes to the same protect list, in the same file, by the same mechanism. The save, replay and campaign formats do not move, so a desktop save opens on a phone and back again.

  • GL Compatibility stays the rendering method on desktop, mobile and the simulator — project.godot:192–193 already says both.
  • Nearest-neighbour texture filtering (project.godot:194) is what the whole art programme is built on and is not negotiable on any platform.
  • Every existing keyboard, mouse and controller binding keeps working, unchanged.
  • Desktop capture gates stay byte-stable because mobile chrome is never constructed there.
  • SideIdentity, the HUD's token ownership, the fog gates and the command snapshots are untouched by every milestone.

Open decisions — three settled, three open

Each of these is a decision this plan deliberately does not take. Three were answered by the user on 2026-08-26 and are marked DECIDED; the rest can be answered while the work runs.

  1. Landscape only? — DECIDED: yes. MB1 declares it (display/window/handheld/orientation="landscape", shipped). A portrait layout is a second HUD, not a setting.
  2. keep or expand? This gates MB7 entirely. keep ships sooner and costs ~18% of a modern phone screen; expand recovers it and brings the safe-area work with it. The plan's default is keep first, expand as a considered follow-up. DECIDED: keep. MB7 stays a later follow-up rather than being deleted.
  3. Per-platform scale_mode=integer on iOS? A measurement for MB9, not a decision now — but the user may want to rule it out in advance, since it is the one setting the desktop playtest already rejected once.
  4. Widen the design canvas? Recommended no (D4's Rejected paragraph says why); worth asking, because it is the obvious-looking alternative to MB7.
  5. Android first? — DECIDED: yes, and both platforms ship. Android establishes the contract (D6) and iOS is MB9. Both toolchains are present, so "both at once" was possible — it is just where ports stall.
  6. Both stores, eventually? Nothing here depends on the answer, but store listings, ratings questionnaires and privacy declarations are work this plan does not contain and someone should own.

Superseded from rev 1

  • "battle.gd:467–531 accepts mouse clicks and action-map presses" — the handler is battle.gd:533–605 and the file is 155 lines longer.
  • "No visible control emits several actions a keyboard supplies" — three lenses, FIRE and END TURN have had buttons since. The dock's scope shrank accordingly.
  • "The 10px action rows are small" — 10 is a font size. The row is 22 px and the failing targets are the 7 px chips.
  • Rev 1's five-slice shape (MB1 Bootstrap, MB2 Controls, MB3 Layout, MB4 Quality, MB5 iOS) — replaced by nine, because "Controls" hid MB2's input classes inside MB3's dock and "Layout" hid the aspect decision inside a milestone that would otherwise just ship.

Carried unchanged from rev 1

  • D1, D3, D5 and D6 in substance — presentation and packaging; completeness before gestures; desktop pixels do not move; Android establishes the contract.
  • The protect list, which becomes R8's and gains the platform APIs by name.
  • The thesis: the engine profile was right and the last metre of interaction is the work. Two months of commits did not change that, only the inventory of what the last metre now contains.

Explicitly out of scope

  • A portrait layout — a second HUD arrangement, a second set of captures and a second set of zoom floors, for a game whose board is 16:9.
  • Any change under core/, ai/, data/ or maps/ — D1 and D9, and the check script that enforces the first of them.
  • Touch-specific balance or content — no mobile board, no mobile tier, no shorter day cap. A phone plays the shipped game.
  • Store listings, ratings, privacy declarations, analytics and crash reporting — real work, none of it this plan's.
  • In-app purchases, cloud saves, achievements, network play — network play is where every other plan has left it.
  • Re-litigating scale_mode on desktop — the playtest that turned it off is recorded in tests/unit/test_texel_stability.gd's own header and pinned there. iOS is a separate platform and a separate measurement.
  • A touch control for fast_forward — the one action in the input map the dock deliberately does not carry. It is held (fast_forward.gd:29–30 polls Input.is_action_pressed), and D2's whole idiom is a chip that synthesises a pressed-then-released InputEventAction, which cannot say "held". The alternatives are a press-and-hold chip with its own timing — a second input convention on the platform where R1 says one tap must make one receipt — or a latched toggle, which is a second piece of pacing state beside the game-speed tier. The tier is the touch player's fast forward, it is a durable device preference rather than a thumb held down, and it is already on a value row in the map menu. Revisit after MB8 reports how the pacing actually reads on a device.
  • A haptics or vibration layer — a nice-to-have that would need its own settings row and its own accessibility argument.
