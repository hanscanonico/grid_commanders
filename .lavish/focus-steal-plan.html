Grid Commanders · Developer ergonomics · Design of record

Focus theft — the smoke sweep and your front window

make smoke opens 49 real Godot windows, one per scenario, and this engine build activates every one of them unconditionally. tools/godot_gui.sh already hands the focus back — measured at 240 ms per window — but forty-nine restored blips in two minutes is still a keyboard you cannot type into, and the sweep now runs unattended from every no-mistakes review worktree. This plan keeps the wrapper as the safety net and attacks the real number: how many windows the sweep opens at all.

PROPOSED — nothing built yet 49 launches → target ≤ 6 tools/ only, plus one presentation seam merge bar: 49 byte-identical captures

1 What actually happens

The complaint — “something keeps stealing my window” — was traced on 2026-07-27 to windowed Godot launches from agent sessions. Nobody is doing anything wrong: the presentation smoke sweep is a windowed gate by design (tools/smoke_scenarios.sh, header: “Needs a display: these runs render”), and both make smoke and the no-mistakes reviewer run it as a matter of course. The bursts observed that afternoon:

20:23 .claude/worktrees/com-33-a0-eventbus-removal make smoke 49

Three sessions, ~67 windows in one afternoon, none of them wanted on screen. The review worktrees carry no bin/ symlink, so they fall back to /opt/homebrew/bin/godot — which resolves to the same /Applications/Godot.app bundle, so this is not a second-engine problem.

2 The measurement — a 240 ms blip, forty-nine times

Sampling the frontmost app every 100 ms (lsappinfo front) across one capture scenario on a warm worktree:

stock wrapper
0.0 s1.0 s2.1 s (scenario ends)
  • +0.42 s — Godot becomes frontmost (org.godotengine.godot)
  • +0.66 s — godot_gui.sh’s watcher fires .godot/activate_pid, your app is front again
  • +2.08 s — the scenario writes its 44 450 B capture and quits

The wrapper works. The problem is arithmetic: 49 × 0.24 s of stolen focus, spread as forty-nine separate interruptions across roughly two minutes, is not a background task — it is a machine you have to stop using.

Two holes in the wrapper the measurement did not hit

tools/godot_gui.sh:56-75 watches for the steal with for _ in $(seq 1 100) and sleep 0.1 — a 10-second budget — and it exit 0s after the first restore. A launch whose window appears later than 10 s (cold worktree, fresh .godot import, the 90-second aiturn scenario) gets no restore at all, and an engine that activates a second time keeps the focus for the rest of the run. Both cases are unobserved so far and both are one slow morning away.

3 Dead ends — tested, refuted, do not re-litigate

The wrapper’s own header already records four failed attempts to stop the steal at the source (no CLI flag, open -g, bundle-id trickery, the no_focus window flag). Two more were tested while writing this plan, because “just tell macOS the app is not a foreground app” is the obvious next idea and somebody will have it again:

AttemptMethodResult
LSUIElement Ad-hoc-signed clone of Godot.app with LSUIElement=true, run over 3 scenarios Still stole focus 3/3. Captures byte-size-identical (44 450 / 61 200 / 83 958 B)
LSBackgroundOnly Same clone with LSBackgroundOnly=true, 3 scenarios Still stole focus 3/3. Same three capture sizes

Both plist routes cost more than they look, too: editing Info.plist inside the signed bundle invalidates the signature and the process is SIGKILLed (exit 137) until you strip com.apple.quarantine and re-sign --deep --sign -. A vendored, re-signed engine copy that still fails the actual goal is the worst of both. The engine activates itself explicitly; macOS metadata does not out-vote that.

4 Decisions

D1 · The sweep’s output is the invariant

Every one of the 49 captures stays byte-identical to today’s, and that byte-diff is the merge bar — the same instrument the balance reports use. Repeated runs already produce identical capture sizes, so the gate is real and cheap.

D2 · No engine-bundle metadata tricks

LSUIElement and LSBackgroundOnly are refuted above, and a vendored re-signed Godot.app would be a supply-chain and licensing liability for zero benefit. The engine binary the repo ships stays untouched.

D3 · A human who launches the game still gets it focused

The existing tty rule stays exactly as written: an interactive launch execs Godot directly, only tty-less agent and script launches get the restore behaviour. This plan makes the agent path better, never the human path worse.

D4 · tools/ first; one presentation seam at most

FS1 is tools/ only. FS2 may touch scenes/battle/battle_setup.gd — where --fog / --map are read off OS.get_cmdline_user_args() — and nothing else. Nothing under core/ or ai/ learns that a smoke sweep exists.

D5 · No new dependency

The Swift activate_pid helper compiled into the gitignored .godot/ cache stays the mechanism, and the open -b <bundleid> fallback stays correct for a machine with no Swift toolchain.

D6 · Fewer windows beats faster restores

The wrapper can only ever shrink a steal it has already suffered. The number that actually decides whether the machine is usable is how many times the sweep boots the engine, and that is FS2’s target — 49 → ≤ 6 — with FS1 as the net underneath it.

5 Milestones

FS0

The instrument — tools/focus_timeline.sh

~40 lines, no engine involvement

Wraps any command and prints the frontmost-app timeline around it, collapsing runs of the same app the way the tables in §2 do. Everything below is stated as a measurement, so the measuring tool ships first — a focus regression is otherwise invisible to make verify forever. 

$ tools/focus_timeline.sh make smoke
  0.00  com.google.Chrome
  0.42  org.godotengine.godot     ← steal   (+0.24s)
  0.66  com.google.Chrome
  ...
  steals: 49   total stolen: 11.8s   longest: 0.31s   restored to wrong app: 1
  • Reports steal count, total and longest stolen interval, and every restore that landed on an app other than the pre-launch one.
  • macOS-only and honest about it: on any other platform it runs the command and says so.
  • Not wired into make verify — it needs a display and a human’s desktop, exactly like the sweep it measures.
FS1

The watcher stops giving up

tools/godot_gui.sh

Three defects, one file, no behaviour change for an interactive launch:

TodayFS1
Watches for ≤ 10 s (seq 1 100 × sleep 0.1), then abandons the run Watches for the child’s whole lifetime — the loop’s exit condition is kill -0 "$game_pid", nothing else
exit 0 after the first restore; a second activation keeps the focus Restores every time the game becomes frontmost, with a short backoff so a fight with a genuinely re-activating engine cannot spin
Restore target is “whoever was front on the last poll”, which caught com.apple.systemuiserver once during testing Prefers the app that was front before the launch; transient system UI (SystemUIServer, Dock, Spotlight, and the game itself) is never adopted as a target

Acceptance. tools/focus_timeline.sh make smoke reports zero stolen intervals longer than 0.5 s, zero restores to an app that was not front before the launch, and the same 49 ok lines. A run started from an interactive terminal still comes up focused.

FS2

One boot per configuration group — 49 windows become ≤ 6

the actual fix

The 49 scenarios are not 49 different programs. They differ in exactly three boot facts — which scene (battle vs. main menu), fog on or off, and which map — and then in a --demo= string the driver dispatches internally. Group by those three and the sweep is a handful of processes:

GroupBootScenarios
battle · default mapbattle.tscn40
battle · fog+ --fog (powermenu+fog, victory+fog)2
battle · the_straits+ --map=the_straits (the naval and power_ready_contrast modes)5
menuno scene argument2

So the driver grows a batch entry — --demos=a,b,c beside today’s --demo= — that runs each scenario, writes its capture, reloads the battle scene, and only quits after the last one. tools/smoke_scenarios.sh keeps its per-scenario output lines and its exit code; what changes is that it launches per group instead of per scenario.

  • All 49 captures byte-identical to a pre-change run (D1). This is the merge bar, not a smoke check.
  • Per-scenario status preserved: a failure still names the scenario, and a scenario that fails in a batch is automatically re-run alone before the sweep reports it.
  • SMOKE_ISOLATE=1 restores today’s one-process-per-scenario behaviour verbatim, so the isolation the sweep has always had remains available in one word.
  • The per-scenario watchdog survives the move: run_with_timeout today only sees a whole group, so the batch driver carries its own per-scenario deadline and fails the group with the offending name.

Acceptance. make smoke opens ≤ 6 windows, the byte-diff over all 49 captures is empty, wall clock is no worse than today, and SMOKE_ISOLATE=1 make smoke is bit-for-bit the old path.

FS3

One boot, full stop — stretch, and only if it is free

stop at FS2 if a single byte moves

The three battle groups only exist because --fog and --map are read once at setup off OS.get_cmdline_user_args() (scenes/battle/battle_setup.gd:46,88). Give BattleSetup an injectable options value and the batch runner can reconfigure between scenarios, collapsing the sweep to one window for the whole run — one 0.24 s blip in two minutes, which is the end state.

This is explicitly the risky half: it makes every scenario share one process with the autoloads (MatchConfig, Settings, Sfx) it used to get fresh. The gate is unchanged and unforgiving — 49 byte-identical captures or the milestone does not ship. FS2 alone already takes the interruption count from 49 to ~4; FS3 is a nicety, not the deliverable.

6 Risks

R1 · A batched scenario passes because of its predecessor high

Shared autoload state is exactly what one-process-per-scenario used to rule out. Mitigation: the byte-diff gate (a leaked pin or a stale Settings value moves pixels), the scene reload between scenarios, and SMOKE_ISOLATE=1 kept as a first-class escape hatch for bisecting a suspicious pass.

R2 · One crash takes a whole group down medium

Today a crashing scenario costs one scenario; batched, it costs 37. Mitigation: a group that fails is re-run scenario-by-scenario before the sweep reports, so the diagnosis a developer reads is always per-scenario — slower only on the runs that were failing anyway.

R3 · The watchdog loses its resolution medium

run_with_timeout polls a process, and a batch process is alive as long as any scenario is progressing — a scenario stuck in _run_demo’s while state != … loop would hide behind its neighbours. Mitigation: the per-scenario deadline moves inside the driver and names the scenario when it trips; the outer timeout becomes a group-level backstop.

R4 · The restore hands focus to the wrong app medium

Observed once during testing: focus came back to com.apple.systemuiserver rather than the browser it was taken from. Rare and self-correcting today, and a lifetime watcher (FS1) makes it more reachable by restoring more often. Mitigation: the pre-launch snapshot and the system-UI denylist are part of FS1, not a follow-up.

R5 · Cold review worktrees widen the window low

Every no-mistakes worktree starts with an empty .godot/: it recompiles activate_pid and imports assets before the first window appears, which is precisely the case today’s 10-second watcher budget can miss. FS1 removes the budget; nothing else is needed.

R6 · Scope creep into the sweep’s coverage low

This is a developer-ergonomics change. It adds no scenario, removes no scenario, and changes no frame. If a milestone starts arguing about what the sweep should photograph, it has left this plan.

7 The merge bar

Same shape as the balance harness’s: generate both sides locally, diff the artefacts, and the change ships only if the diff is empty. 

# before — on the unchanged tree
SMOKE_KEEP=1 tools/smoke_scenarios.sh 2>&1 | tail -3      # prints the capture dir
cp -R <that dir> /tmp/smoke-before

# after — with the change applied
SMOKE_KEEP=1 tools/smoke_scenarios.sh 2>&1 | tail -3
diff -r /tmp/smoke-before <the new dir>                   # must be empty: 49 files, byte-identical

# and the thing this plan is actually about
tools/focus_timeline.sh make smoke                        # steals: ≤6, longest ≤0.5s, wrong-app restores: 0
  • make verify stays green — it never touched the sweep and still does not.
  • make screenshot stays byte-stable; it is one launch through the same wrapper and FS1 must not perturb it.
  • The interactive path is checked by a human running make run once and finding the window in front of them.

8 Out of scope

  • Making the sweep headless. Godot’s macOS headless display server draws nothing, and the sweep’s entire premise is that a frame gets rendered — SMOKE_MIN_BYTES exists to catch exactly the blank capture this would produce.
  • Injecting into the engine (DYLD_INSERT_LIBRARIES, swizzling -[NSApplication activate…]). It would work and it would be the worst thing in the repository: it needs library validation disabled on a re-signed engine copy, and it fails silently and mysteriously on the next engine bump.
  • Vendoring a patched engine. Same objection, larger. The plan’s whole point is that the repo keeps running the stock build.
  • Teaching the agents not to run smoke. They are supposed to run it — that is the gate working. Making the gate quiet is the fix; making it rarer is a regression.
  • A settings toggle to skip the sweep. Nobody would set it back.
