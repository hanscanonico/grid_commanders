Grid Commanders · Stretch item · Proposed for review · rev 1

Match Replay — watch it again, and read what the computer did wrong

A match ends and it is gone. This plan keeps it. Every match records itself to a rotating slot as it is played; any recording plays back in the battle scene with the real animations, cut-ins and banners, at whatever speed you like, pausable and steppable; and an offline pass reads one and reports the computer's obvious mistakes — the unit that stood still all game, the funds never spent, the Command Power banked to the last day, the tank walked into three guns.

Nothing here is a new simulation. A replay is an opening board and the commands that were applied to it, played back through the same pipeline the computer's own turns go through. CLAUDE.md's third architecture rule already named this as what the command pattern was for: "a serializable log for save/replay". This is the second half of that sentence, collected.

Commands, not frames Nothing under core/ or ai/ gains a hook Every match records itself A replay verifies itself or halts
1

The seams already exist

Every part this needs is already built, tested and load-bearing. What is missing is that none of them have been introduced to each other, and that the one log the repo does write is descriptive rather than replayable.

Determinism is already a promise, and it is narrow

Same seed plus same commands ⇒ same result, stated in CLAUDE.md and true because the match RNG has exactly one consumer in the whole repo: core/rules/combat_resolver.gd:343. Everything else — capture points, income, repair, upkeep, doctrine hooks — is integer arithmetic over public state. A replay does not have to reproduce a match; it only has to re-issue it.

There is exactly one place a live command is applied

scenes/battle/battle_command_pipeline.gd is the live scene's single mutation seam, and tools/check_scripts.sh fails the build if a second .apply(game) appears anywhere under scenes/battle. The recorder needs one call site and the repo already guarantees there is only one to find. tools/balance/match_engine.gd is the headless twin, and it already brokers before_apply / after_apply for the Balance Lab.

A whole board already serialises, validator included

SaveCodec.encode(state, ai_teams, difficulty) states map path, roster, sides, seats, fog, funds, owners, capture progress, home HQs, every unit, every commander's charge — and rng_state. It is version 7, additive, and decode refuses a board no seating could have produced, field by field. A replay's opening frame is that dictionary, unchanged, which is also why a replay of a resumed save needs no thought at all.

A per-command log already exists — and is not replayable

BalanceMatchRecorder._log_entry (tools/balance/match_recorder.gd:500) writes one JSONL record per applied command: type, from, to, damage, deaths. It is deliberately deterministic and clock-free. But it names a unit by its type id — "infantry" — which answers "what happened" and cannot answer "do it again". One field's worth of difference, and the reason RP1 is a new codec rather than a flag on that one.

A driver that is not a player already exists

scenes/battle/battle_ai_runner.gd is 110 lines that feed commands into Battle.execute_command, await conclude_command, pace off Settings.speed and stop at Battle.pause_gate(). The replay runner is that file with the planner swapped for a cursor into an array — every animation, cut-in, banner, elimination card and victory lockup comes along for free.

Every counterfactual the analyser wants is a public static

AttackRange.threat_cells / ring_cells / ready_shot, MovementResolver.reachable, and CombatResolver.forecast_at — which takes the defender's cell precisely so a caller can ask "how hard am I hit if I stop here?" without standing a unit there. "What could this unit have done instead?" is a question the rules already answer for the planner; the analyser asks the same authorities, and never the planner (D6).

2

What a replay is

A JSONL stream: one header line stating the opening board, then one line per applied command, appended as the match plays. Not a movie, not a series of states, and not a screen recording — the file holds only what a human or a planner decided, and the sim works out the rest exactly as it did the first time.

opening envelope→ SaveCodec.decode→ GameState→ command #1 … #n→ BattleCommandPipeline→ the same match 
// line 0 — the header. `opening` is a SaveCodec envelope, verbatim.
{"replay": 1, "recorded": "2026-08-01T18:04:22", "label": "Ironworks · Alina Ward vs Cass Orlov",
 "opening": { "version": 7, "map_path": "res://maps/ironworks.txt", "day": 1, "rng_state": "4083…", … }}

// then one line per command that was actually applied.
{"n":0, "d":1, "t":1, "c":"move",    "at":[3,7], "path":[[3,7],[4,7],[5,7]],            "ck":1917348201}
{"n":1, "d":1, "t":1, "c":"capture", "at":[8,2], "path":[[8,2],[8,3]],                    "ck": 733910044}
{"n":2, "d":1, "t":1, "c":"build",   "cell":[2,9], "unit":"mech",                          "ck":2044118876}
{"n":3, "d":1, "t":1, "c":"attack",  "at":[6,4], "path":[[6,4]], "target":[7,4],           "ck": 158802391}
{"n":4, "d":1, "t":1, "c":"end_turn",                                                "ck":1290334517}

Which unit? The cell it acted from.

at is path[0], and it is unambiguous because a carried unit can never act — MoveCommand.validate_path_steps refuses one outright — so every unit that can appear in this field is alone on its cell. No ids to mint, no index to keep in step, and the log stays readable by eye. DropCommand's named passenger is the one exception and rides as a cargo index, deterministic because GameState.cargo_of walks state.units in order.

ck — the board after, in one integer.

A cheap deterministic digest of day, hand, funds, owners and every unit's cell and health. Written on record, checked on playback. It is what turns "this replay is from before you retuned the Mech" from a silently different match into a named halt at command #114 (D3).

Rejected commands are not in it.

The recorder sits after apply(). A plan the pipeline refused never touched the board, so it never touched the file — which is what keeps "re-apply every line in order" a complete description of the match rather than a description plus a filter.

Size: a 20-day AI-versus-AI match is roughly 400–700 commands, so ~60–100 KB of JSON. Ten rotating slots cost under a megabyte in user://replays/.

3

Decisions

Seven, all proposed rather than locked. D3 (self-verifying) and D6 (the analyser's discipline) are the two that decide whether this feature ages well; D5 is the most taste-shaped.

D1 · A replay is an opening envelope and a command log proposed

The opening is SaveCodec.encode(state, ai_teams, difficulty) verbatim, taken in Battle._ready immediately after BattleSetup.build and before a single command. Not a MatchRequest, and not the map path plus a seed: the envelope already carries the roster, the seating, the grouping, the fog flag, the commanders with their charge, the day-1 board after TurnRules.begin_turn has run inside GameState.create, and rng_state itself — so a replay starts from a board rather than from a recipe for one. Two things fall out for free: a match resumed from a save records correctly from wherever it was picked up, and the format inherits SaveCodec's whole total validator instead of growing a second one. Rejected: recording map + seed + setup and rebuilding by re-running create — one more independent opinion about what a match opens as, which is the drift the four-players and open-seats plans both spent a decision preventing.

D2 · The recorder observes, at the two brokers that already exist proposed

Balance plan D2 restated for a second instrument: nothing under core/ or ai/ gains a signal, a hook or a field. There are exactly two call sites, and both are places a command already changes hands: BattleCommandPipeline.execute after command.apply(game), and BalanceMatchEngine.play beside its existing recorder.after_apply. The first is the live scene's single mutation seam and tools/check_scripts.sh already fails a build that grows a second one, so "one call site" is enforced rather than remembered. What is recorded is therefore bit-for-bit the shipped game, and the recording cannot bend the game toward being recordable.

D3 · A replay verifies itself, or halts and says where proposed

Every entry carries ck, a digest of the board the command left behind. Playback recomputes it after each apply and stops at the first mismatch, naming the command index, the day and the side. This is not paranoia about the sim — it is the honest answer to the one thing a command log cannot survive: the game changing underneath it. Retune a .tres, fix a rule, add a doctrine hook, and yesterday's replay is describing a match this build would not play. Without the digest it would quietly play a different match and look fine. With it, the halt is also the diagnostic — the seq number names the exact command whose meaning moved, which is a genuinely useful thing to hand a bisect. A replay is disposable: nothing resumes from one, nothing is scored off one, and a stale one is deleted rather than migrated. That is what buys the right to have no upgrade path.

D4 · Playback is presentation; the sim never learns it is a replay proposed

BattleReplayRunner is BattleAiRunner's sibling: it feeds recorded commands to Battle.execute_command, awaits conclude_command, paces off Settings.speed and holds at Battle.pause_gate() — the same boundary that already keeps "no interactive menu under a banner or a cut-in" true for computer turns. No planner is built (a replay has nothing to decide), and — the load-bearing half — game.fog_enabled is not touched. Fog is an input to MoveCommand.validate and to GameState.advance_unit's ambush, so a replay that switched it off would resolve the recorded moves differently and every ambush in the match would evaporate. Omniscience is therefore a flag on scenes/battle/battle_perspective.gd — the one adapter from the vision authority to viewer policy — and nowhere else.

D5 · The viewer is omniscient, and the recording is always on proposed

Omniscient: a replay shows the whole board whatever fog the match was played under. The match is over, so there is nobody to hide it from — and a fogged AI-versus-AI match watched through one army's eyes is mostly a black rectangle, which is the opposite of the point. The blackout a hot-seat handoff raises is skipped for the same reason: nobody is being handed the device. Always on: every match records itself into user://replays/, oldest pruned past ten, appended per command so a crash costs the tail rather than the file. The interesting match is the one you did not know was interesting until it ended, and a feature you have to remember to arm is a feature that is off when it matters. Rejected: an opt-in --record flag, and a single slot mirroring save.json — the first fails the sentence above, the second means the match you want is always the one before the one you just played.

D6 · The analyser asks the rules; it never asks the planner proposed

Every counterfactual comes from AttackRange, MovementResolver and CombatResolver.forecast_at — the same authorities the planner itself scores through, which is exactly why a finding drawn from them is a finding about the game rather than about one revision of ai/. Nothing under ai/ gains a why-hook, no "reason" string is threaded out of a planner, and no report ever claims to know what the computer was thinking. A finding says what happened, what was available instead, and what the difference was worth; the judgement stays with the reader. This is the same line balance plan D2 drew — the instrument observes, and the observed thing is the shipped one — and it is what keeps the analyser useful after the planner is rewritten. Corollary: a finding is evidence, never a gate. make replay-report stays out of make verify, because several detectors fire on a doctrine playing exactly as it is meant to.

D7 · --watch stays; --replay is a second instrument proposed

Today's --watch re-plans a Balance Lab row from its seed and is the balance plan's BS3 replay-fidelity check: it is supposed to diverge when the AI changes, and BattleOutcome's one diffable line is what proves the window and the CSV agree. --replay= is the opposite by design — immune to AI changes, because the decisions are in the file. Both ship, both keep their own Makefile target, and neither is described in terms of the other. What the Lab gains is --replays: one recording per match, named by match_id, so a suspicious row in matches.csv becomes a file you can watch and feed to the analyser.

4

Milestones — each one shippable

RP1 · The format and the recorder size M · core + two call sites

Two new Node-free files, both driven directly by GUT. core/replay_codec.gd (ReplayCodec) is pure: encode_command(Command) → Dictionary, command_from(GameState, Dictionary) → Command, checkpoint(GameState) → int, and an envelope validator built the way SaveCodec.KEY_RULES is — one table, presence and shape read off it, because two lists that have to agree by hand is the drift COM-54 was about. core/replay_file.gd (ReplayFile) is storage only, in SaveGame's tradition: open a slot under user://replays/, append, close, list() summaries, prune past ten.

Wired in at the two brokers of D2, plus --replays on tools/run_balance_sim.gd.

The merge bar is tests/unit/test_replay_fidelity.gd: play a seeded AI-versus-AI match through BalanceMatchEngine with a writer attached, re-apply the log to a fresh state, and assert every checkpoint matches and the final boards are identical, unit for unit. tests/unit/test_replay_codec.gd round-trips every command class beside it, including a Drop with a named passenger and a move an ambush cut short.

RP2 · Watching one size M · scene layer

  • MatchRequest.replay_path and --replay=<path>, read through CmdArgs like every other flag — so a replay boot and a menu launch reach the board by the same route.
  • BattleSetup.build builds a replay's state from the envelope through the same SaveCodec.decode path resume already uses, and hands Battle the command list.
  • scenes/battle/battle_replay_runner.gd — the runner of D4.
  • BattlePerspective gains the omniscient flag; the handoff blackout is skipped in replay mode.
  • Controls: Esc pauses through the existing request_pause / pause_gate seam onto a replay-flavoured menu (Resume · Restart · Main Menu); a step key advances one command while paused; speed is the existing device preference. Battle.STATE_CONTEXT gains the legend, so the top bar prints keys that work here — never refreshed from the call sites.
  • make replay REPLAY=<path>, windowed through tools/godot_gui.sh like every GUI target.

RP3 · Finding one size S · menu

A Replays row on the main menu opening a list built from ReplayFile.list() — board, days played, who sat where, how it ended — each entry staging a MatchRequest with replay_path and changing scene. It gets the capture gate its siblings have (SeatStrip.layout_error's shape, and for its reason: an unsorted list stacks at the container's origin and photographs as a bare panel) and a menu_replays scenario in the smoke sweep.

RP4 · Reading one size M · tools only

tools/replay/replay_analysis.gd (Node-free) plus tools/run_replay_report.gd and make replay-report REPLAY=…, writing reports/replay_<id>.md and .json — gitignored, like every other report. It re-applies the log to a fresh state and, at each decision point, compares what was done with what the rules say was available:

findingwhat it asks
idle_unita ready unit ended its turn without moving or firing while an enemy or a takeable property was in reach
hoardingfunds ≥ the cheapest buildable at an owned, empty production property at end of turn
walk_into_firea move ended on a cell whose incoming threat (AttackRange.threat_cells) ≥ the unit's health, with no shot fired
worse_shotan attack was taken when another target in range had a strictly better forecast_at (dealt minus countered)
missed_capturea capture-capable unit could reach a property its side does not hold, and did something else
banked_powera full meter carried for N of the owner's own turns — the Vanish-stall class, from the commander-doctrine plan
oscillationa unit returned to a cell it held two turns earlier, having acted in neither
stranded_transporta loaded transport made no progress toward a legal drop for N turns — naval R1's known hole, measured
undefended_hqan enemy stood within one turn's reach of a home HQ with nothing able to contest it

Findings are ranked evidence carrying day, side, unit, cell and the counterfactual. Tests are hand-authored fixture logs in which each detector must fire exactly once — a detector with no fixture is a detector nobody can trust.

5

Risks

R1 · A data or rules edit invalidates every existing replay

Certain, not hypothetical — the repo retunes .tres files as a matter of course. D3's checkpoint converts it from a silent lie into a named halt, and D5's "replays are disposable" is what makes that acceptable: nothing resumes from one, so there is no migration to owe. Watch item: if the halt turns out to fire on ordinary balance passes often enough to be annoying, the answer is to stamp the data revision in the header and refuse up front with a clearer message — not to weaken the digest.

R2 · The one guarded live seam gains a side effect

Recording adds a call inside BattleCommandPipeline.execute, the file check_scripts.sh holds to exactly one apply and one validate. The call is a single record after apply writing to an append-only stream, so the greps are unaffected — but the invariant is worth naming here, because "the pipeline gained a second responsibility" is how a seam stops being one.

R3 · Analyser false positives

Several detectors fire on a doctrine playing correctly — Sable Wren sitting in woods is idle_unit; a commander whose power wants a particular board state is banked_power. Mitigation is honesty about what the instrument is (D6: evidence, never a gate, never in make verify) and tuning the N-thresholds against a real recorded match rather than a fixture.

R4 · Playback diverges on something the log does not carry

The whole design rests on the sim reading nothing but the board, the commands and the seeded RNG. Today that is true and narrowly so — one RNG consumer, no clock in core/, GameSpeed forbidden from reaching it. RP1's fidelity test is the standing proof, and it belongs in make test so a future change that quietly widens the input surface fails there rather than in a report nobody ran.

R5 · Disk and privacy

Bounded by construction: ten slots, ~100 KB each, in user:// beside the save and the settings. A replay holds board coordinates and nothing else — no paths on disk beyond the res:// map path the save format already stores, and no player identity, because the game has none.

6

Explicitly out of scope

  • Replays as saves. A replay never resumes into a playable match, and save.json is untouched. Two formats with two jobs; the moment one is asked to do the other's, D3's "disposable" stops being true and R1 becomes a migration problem.
  • Rewind and scrubbing. Step forward and pause, yes. Seeking backwards means replaying from the opening to the target command, which is buildable on exactly this format later and is not worth the interface now.
  • Branching from a replay ("what if I had gone left?"). It is the natural next idea and it is a different feature — it needs a match to fork into, which is the save format's job, not this one's.
  • Video export. Out of scope here and already parked elsewhere — the promo-recording work has its own branch.
  • A why-hook in the planner. D6. Whatever the analyser cannot infer from the rules, it does not report.
  • Retuning anything. This plan ships an instrument. Acting on what it finds is a separate pass with its own merge bar — make commander-balance and make difficulty-check, as always.
